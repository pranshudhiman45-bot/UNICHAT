# Deploying Unichat: Vercel (web) + Render (API)

Order matters because each side needs the other's URL: **database, then API, then web, then one small API update.**

## 1. Database: MongoDB Atlas (free)
1. Create a free M0 cluster, a database user, and under *Network Access* allow `0.0.0.0/0`.
2. Copy the connection string and add a database name, e.g.
   `mongodb+srv://USER:PASSWORD@cluster0.xxxxx.mongodb.net/unichat?retryWrites=true&w=majority`

## 2. API on Render
1. Render dashboard, *New*, *Blueprint*, pick this GitHub repo. It reads `render.yaml` at the repo root.
2. Fill the three values it asks for:

| Variable | Value |
|---|---|
| `MONGODB_URI` | the Atlas string from step 1 |
| `PUBLIC_API_URL` | `https://<service-name>.onrender.com/api` |
| `CLIENT_URL` and `ALLOWED_ORIGINS` | placeholder for now (`https://placeholder.vercel.app`); fixed in step 4 |

3. Deploy. When it is live, open `https://<service-name>.onrender.com/api/health`. It must return `{"ok":true}`.

Secrets (`JWT_SECRET`, `JWT_REFRESH_SECRET`, `PASSWORD_RESET_PEPPER`) are generated by Render. Do not reuse your local ones.

## 3. Web on Vercel
1. *Add New Project*, import the same repo, and set **Root Directory = `web`** (framework preset: Vite).
2. Add the **frontend environment variables**. They are public URLs, not secrets:

```env
VITE_API_URL=https://<service-name>.onrender.com/api
VITE_SOCKET_URL=https://<service-name>.onrender.com
```

   Use your real Render hostname and no trailing slash. The values are baked in at build time, so changing them later needs a redeploy.
3. Deploy and note the URL, e.g. `https://unichat-xyz.vercel.app`.

## 4. Point the API at the web app
In Render, *Environment*, set both to the exact Vercel origin (no trailing slash, no path) and save, which redeploys:

```env
CLIENT_URL=https://unichat-xyz.vercel.app
ALLOWED_ORIGINS=https://unichat-xyz.vercel.app
```

Open the Vercel URL, register, create a workspace, and send a message.

## Why these settings
- `COOKIE_SAMESITE=none`: Vercel and Render are different sites, so the login refresh cookie must be a cross-site cookie (it is still HttpOnly and Secure). Without it you would be logged out on every reload. Safari blocks third-party cookies, so Safari users may be logged out on reload. Use Chrome, Edge or Firefox for the demo.
- `TRUST_PROXY_HOPS=1`: Render sits behind one proxy, so rate limits see the real client.
- The Socket.IO connection goes straight to Render and authenticates with the token, not a cookie.

## Demo profile limits (what `render.yaml` sets)
`NODE_ENV=staging` skips the production-only requirements so you can deploy without Cloudinary or SMTP:
- Email verification is off, and password-reset codes are not emailed (`EMAIL_TRANSPORT=file`).
- Uploads use the server disk (`FILE_STORAGE=local`), which Render's free tier erases on restart and redeploy.
- Free Render services sleep after ~15 min idle; the first request then takes ~30-60 s. Open the API health URL before a demo to wake it.
- No Redis, so run exactly one instance.

For a hardened production setup use `NODE_ENV=production` and configure Cloudinary, SMTP, `ADMIN_EMAIL` / `ADMIN_PASSWORD_HASH`, and Redis as described in [PRODUCTION.md](PRODUCTION.md).

## Troubleshooting
| Symptom | Cause |
|---|---|
| Browser console shows a CORS error | `ALLOWED_ORIGINS` does not exactly match the Vercel origin |
| Login works, but reload logs you out | `COOKIE_SAMESITE` not `none`, or you are using Safari |
| "Failed to fetch" / long first load | Render free service is waking up |
| Page 404 on refresh at `/chat/...` | Root Directory not set to `web` (so `vercel.json` is ignored) |
| Live updates missing | `VITE_SOCKET_URL` wrong, or the frontend was not redeployed after changing it |
